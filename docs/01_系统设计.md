## 1. 总体架构

```mermaid
flowchart TB
    subgraph FE[前端 React SPA]
        P1[工作台总览] --- P2[备货建议表] --- P3[预警中心] --- P4[采购计划] --- P5[AI问答助手] --- P6[数据中心/设置]
    end

    subgraph API[后端 FastAPI 单层API]
        R1[/api/skus/] --- R2[/api/calc/] --- R3[/api/suggestions/] --- R4[/api/alerts/] --- R5[/api/purchase-orders/] --- R6[/api/chat/]
    end

    subgraph CORE[核心域服务 可插拔]
        DS[数据源适配器层<br>DataSource Registry]
        EG[测算引擎<br>Modifier Pipeline]
        RL[预警规则引擎<br>Rule Registry]
        NT[通知器<br>Notifier Registry]
        QA[问答编排器<br>Intent → 域服务]
    end

    subgraph DB[(SQLite / PostgreSQL)]
        T1[sku_master] --- T2[daily_sales] --- T3[inventory_snapshot] --- T4[external_signals] --- T5[calc_result] --- T6[alert] --- T7[purchase_order] --- T8[settings]
    end

    FE --> API --> CORE --> DB
    SCH[APScheduler<br>每日06:30测算] --> EG
```

**设计要点：**
- 单体仓库（monorepo）双进程：`backend/`（FastAPI）+ `frontend/`（React+Vite），SQLite 单文件起步，连接串可切换 PostgreSQL。
- **一切外部数据先进 `external_signals`/`daily_sales` 等标准表，测算引擎只读标准表**——数据源怎么进来、引擎怎么算、结果给谁用，三层互不感知。
- 计算结果落表（`calc_result`），页面只读结果表。测算慢、页面快，且结果可审计、可回测。

## 2. 模块清单与可插拔设计

| 模块 | 职责 | 可插拔？ | 说明 |
|---|---|---|---|
| M0 工程骨架 | 项目脚手架、配置、数据库迁移、健康检查 | —— | 所有模块的地基 |
| M1 数据源适配器 | CSV 导入 / API 同步 → 标准表 | ✅ 可插拔 | 实现 `DataSourceAdapter` 接口并注册即可新增数据源；互相零依赖 |
| M2 测算引擎 | 基线日销 → 系数修正 → 评分 → 备货量 | ✅ 可插拔（系数修正器） | 趋势/竞争/事件/环境四个修正器各自独立注册；但引擎整体**联动 M1**（读标准表）、**被 M3/M4 依赖**（写 calc_result） |
| M3 备货建议表 | 读 calc_result 展示、人工调整、导出 | 🔗 联动 M2 | 只读结果表 + 写人工覆盖字段，不感知计算逻辑 |
| M4 预警中心 | 规则判定、通知、处理状态 | ✅ 规则可插拔；🔗 联动 M2、M5(通知) | 新增规则 = 注册一个判定函数；通知渠道独立注册 |
| M5 采购计划 | 建议→采购单、预算校验、交期倒排、到货回写 | 🔗 联动 M3（读确认的建议）、M1（回写在途） | 单据状态机独立，不可拔但边界清晰 |
| M6 工作台总览 | 聚合 KPI 卡片、待办 | 🔗 联动 M2/M4/M5 | 纯聚合只读页，各模块提供统计接口即插 |
| M7 AI 问答助手 | 意图识别 → 调域服务 → 组装回答 | 🔗 联动 M2/M3/M4/M5 | 只读各域公开接口 + 触发动作；新增意图=新增一个 handler |
| M8 设置中心 | 参数/阈值/系数档位/SKU 参数 | 🔗 被所有模块读 | 全系统唯一写参数的地方 |

**可插拔契约（写入 CLAUDE.md 强制执行）：**
1. 适配器：`class XxxAdapter(DataSourceAdapter)`，实现 `fetch() -> list[RawRecord]` 与 `normalize() -> list[StandardRecord]`，在 `datasources/registry.py` 注册。
2. 修正器：`class XxxModifier(Modifier)`，实现 `factor(sku, ctx) -> tuple[float, str]`（返回系数与人话依据），注册进 `engine/modifiers/`。
3. 预警规则：`rule(code, level, condition_fn, advice_fn)` 装饰器注册。
4. 通知器：`Notifier.send(alert)`，站内信与邮件两个实现并存。
5. 任何可插拔单元被移除（注销）后，系统必须**降级可用**：缺修正器按系数 1.0 计算并在依据中注明；缺通知器仅站内可见。

## 5. 关键业务流程（实现口径）

1. **每日 06:30**：调度器依次执行 → 各已启用适配器同步 → 数据校验（缺数沿用上一期并标记）→ 测算引擎全量重算 → 预警规则扫描 → 通知发送。
2. **预测日销**：`base = 近30天日销×0.5 + 近90天日销×0.3 + 去年同期日销×0.2`（缺去年数据权重转 0.6/0.4；断货日剔除）；`forecast = base × Π各修正器系数`。
3. **备货评分**：缺货紧迫 40 + 销售健康 25 + 外部信号 25 + 资金效率 10；分档 ≥80/60~79/40~59/<40。
4. **建议备货量**：`forecast × (生产+头程+上架 + 安全天数) − 可售库存 − 在途`，负值取 0，再按 MOQ 向上取整。
5. **采购计划**：勾选建议 → 按（供应商， 目的仓）分组生成草稿 → 预算校验（超预算仅提示）→ 交期倒排（大促截止日 − 头程 − 上架，海运来不及则提示改空运）→ 确认 → 到货回写在途与库存。

## 6. 非功能与验收

- 性能：SKU ≤ 500，全量测算 < 60s；接口 P95 < 500ms。
- 所有阈值、系数档位、权重、备货周期均可经 settings 表在页面修改，代码零硬编码。
- 验收：mock 数据全链路跑通（导入→测算→建议→预警→采购→回写）；5 个 SKU 手工验算一致；断货/滞销预警正确触发。
